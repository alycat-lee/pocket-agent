# 15 · 能力等效目标体系（项目北极星与测评基准）

> 本文档是项目的纲领性文件，优先级高于所有功能 Phase。它回答三个问题：目标是什么（8B + 框架 ≈ 32B/百B 大模型能力效果）、怎么衡量（能力维度 × 三方对跑基准）、下一步做什么由什么决定（雷达图缺口）。

## 1. 北极星定义

**让 8B 级本地小模型通过工程框架获得 32B~100B+ 大模型的上下文与功能效果，将本地部署门槛降到 8G 显存。**

推论的两条设计铁律：

1. **一切机制立项必须回答"补的是哪个能力维度"**——补不了任何维度的功能不做
2. **一切效果以三方对比测量为准**——裸 8B / 8B+框架 / 云端大模型，感觉不算数，数据算数

## 2. 能力维度矩阵（等效地图）

| 维度 | 大模型内力 | 小模型外挂方案 | 当前状态 | 测量任务示例 |
|---|---|---|---|---|
| D1 指令遵循与格式 | 内生 | 约束解码（json_schema/grammar） | ✅ 已补平 | 10 种格式约束输出，解析成功率 |
| D2 上下文与记忆 | 长窗口 | 压缩 + 预算 + 会话层 + 实体槽位 | ✅ 已补平 | needle 测试：第 1 轮埋信息，第 10 轮取回 |
| D3 工具使用 | 自主规划 | 状态机 + 账本 + 护栏 | ✅ 已补平 | 3~6 步多工具任务，零重复真实调用 |
| D4 任务理解与规划 | 内生推理 | Planner 任务卡（Phase 27） | ⚠️ 待建 | "生成 2 万字小说"类复合指令的类型/约束提取正确率 |
| D5 自我校验纠错 | 内生反思 | Verifier 验收关卡（Phase 27） | ⚠️ 待建 | 故意注入思维链/泄漏文本，拦截率 |
| D6 长程连贯生成 | 一口气写完 | writer 四段式（大纲+一致性卡+接缝） | ⚠️ 已建未验收 | 3000 字文章：重叠率 / 数字一致性 / 大纲覆盖率 |
| D7 知识获取 | 预训练记忆 | 搜索工具 + RAG | ❌ 未建 | 时效性问题（"2026 年最新…"）回答正确率 |
| D8 推理深度 | 思维链内力 | 分步推理 / 自洽投票 / 云端路由 | ❌ 未建 | 多跳数学题、逻辑题正确率 |
| D9 多轮状态 | 内生 | rewrite + 会话摘要 | ✅ 基本补平 | 指代跟随三连问成功率 |

**等效判定标准**：单维度上 "8B+框架" 达到云端大模型成绩的 80% 即视为补平；D8（推理深度）允许豁免——该维度工程只能缓解不能补平，诚实标注为"需云端混合"。

## 3. 测评基准（eval_benchmark）

在现有 `scripts/eval.py` 基础上升级为三跑道基准：

```
benchmark/
├── tasks/
│   ├── d1_format.json        # 每维度 5~10 个任务
│   ├── d2_memory.json
│   ├── ...（d3~d9）
│   └── README.md             # 每题的评分 rubric
├── runners/
│   ├── bare.py               # 跑道 A：裸 8B 自由对话（无框架）
│   ├── pocket.py             # 跑道 B：8B + pocket-agent 全机制
│   └── cloud.py              # 跑道 C：DeepSeek API（能力天花板参照）
└── report.py                 # 汇总：维度雷达图 + 明细表 → benchmark_report.md
```

**任务卡格式**：`{id, dimension, input, rubric: {pass_criteria: [...], score_fields: [...]}, expected_constraints}`

**评分方式分层**：
- 客观指标（自动）：格式解析率、重复调用率、字数达标率、needle 命中率、数字一致性
- rubric 评分（半自动）：用云端大模型按评分标准打分（judge），人抽查 10% 校准
- 每次运行产出三跑道 × 九维度的得分表与雷达图，落盘存档可对比历史

**纪律**：
- 每个 Phase 立项时声明目标维度，验收时跑对应维度的基准对比
- 基准任务集只增不改（改了就无法纵向对比）；新事故原句必须收录进对应维度
- 每月或每 5 个 Phase 跑一次全量基准，雷达图归档

## 4. 由基准驱动的近期路线

```
Phase 26/27（D4/D5/D6）→ 跑基准验证补平 →
缺口预测：D7（知识）大概率成为下一个最大缺口 → 搜索/RAG 工具
D8 不硬补：云端混合路由，把"推理深度"标注为混合架构场景
```

Phase 26/27 的定位修正：不是"事故修复"，是 D4/D5/D6 三个维度的能力建设，验收标准从"事故原句能跑通"升级为"对应维度基准成绩 ≥ 云端 80%"。

## Phase 28 · 能力等效评测基准

````
@docs/03-模块实现规格.md @pocket-agent-docs/15-能力等效目标体系.md

实现三跑道能力基准（文档 15 §3 全文规格）：

1. benchmark/ 目录结构：tasks/（d1~d9 九个 JSON 任务集，
   每维度先收录 5 个任务，事故原句入 d4）、runners/、report.py
2. 三个跑道实现：
   - bare.py：直接对 llama-server 发多轮自由对话，无任何框架机制
   - pocket.py：走 SessionManager 完整链路
   - cloud.py：DeepSeek API（复用 llm-deepseek 的 client），
     DEEPSEEK_API_KEY 缺失时跳过并标注
3. 评分器：客观指标全自动；rubric 项用 cloud 跑道模型当 judge
   （评分 prompt 固定模板，含评分标准与 1~5 分制）；
   judge 结果连同依据一起落盘供人工抽查
4. report.py：输出维度得分表（三跑道并列）+ 终端 ASCII 雷达图 +
   benchmark_report.md（含与上次运行的差值对比）
5. 接入现有 eval.py：保留原工具调用指标，基准作为
   scripts/eval.py --benchmark 子命令
6. 测试：任务集 schema 校验、评分器对已知输入的确定性、
   报告生成格式

验收：llama-server 运行中执行
python scripts/eval.py --benchmark --dims d1,d2,d3
产出三跑道对比报告；d4~d9 在 Phase 26/27 完成后全量跑通。
````

## 注意事项

1. 本文档放入 pocket-agent-docs/ 后，建议在 README 顶部加一行链接并标注"纲领文件"——今后每个新 Phase 的第一行都应该写"目标维度：DX"
2. 云端跑道不是作弊是标尺：它的成绩定义了"100B 效果"在哪，框架的价值 = 跑道 B 与跑道 A 的分差，天花板 = 跑道 C
3. judge 用云端模型有成本，日常迭代只跑客观指标维度，里程碑节点才跑全量 rubric
4. 警惕为基准过拟合：基准任务只增不改，但每季度应新增一批没见过的任务验证泛化——等效能力要的是泛化，不是背题
