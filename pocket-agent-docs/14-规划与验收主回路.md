# 14 · 规划与验收主回路（Phase 27）

> 定位：这不是又一次 bug 修复，是补 Agent 主回路缺失的两环——规划（Planner）与验收（Verifier）。前置认知：Phase 13 的四个根因修复仍然要做（它们是真 bug），但核心病因是主回路缺环：任务从进门到出门，没有经过"理解 → 规划 → 验收"。

## 主回路现状与目标

```
现状：输入 → [意图三分类] → 硬编码分支 → 状态机执行 → 输出直达用户
目标：输入 → Planner（任务卡）→ 执行器分派 → 执行 → Verifier 验收 → 交付/打回
```

设计原则延续原子化思想：**小模型不做开放式规划，只做结构化输出**——Planner 是一次 generate_json 约束解码调用，产出任务卡；Verifier 是纯代码校验，不调模型。

## 1. 任务卡（task.py 新模块）

```python
@dataclass
class TaskCard:
    type: Literal["qa", "agent", "writer"]
    goal: str                    # 一句话任务目标
    constraints: dict            # {"total_chars": 20000, "language": "zh", ...}
    plan: list[str]              # 计划步骤（3~7 条，writer 时为大纲思路）
    needs_history: bool          # 是否需要注入会话历史（替代 _compose_run_task 的猜测）

TASK_CARD_SCHEMA = {
    "type": "object",
    "properties": {
        "type": {"type": "string", "enum": ["qa", "agent", "writer"]},
        "goal": {"type": "string"},
        "constraints": {"type": "object"},
        "plan": {"type": "array", "items": {"type": "string"}},
        "needs_history": {"type": "boolean"},
    },
    "required": ["type", "goal", "constraints", "plan", "needs_history"],
}
```

**PLANNER 提示词**（录入 prompts.py，逐字）：

```
分析用户任务，输出任务卡 JSON。

要求：
1. type：直接问答=qa，需要工具=agent，创作长文=writer
2. goal：一句话概括目标
3. constraints：提取所有硬性要求（字数、格式、语言等），
   字数统一换算为数字（"2万字" → "total_chars": 20000）
4. plan：3~7 个执行步骤，每步一句话
5. needs_history：任务是否依赖之前的对话内容

会话摘要：{rolling_summary}
用户任务：{user_input}

只输出 JSON。
```

**与旧组件的关系**：任务卡的 `type` 字段取代意图路由（IntentRouter 降级为 Planner 失败时的快速兜底，保留规则路径作为 fallback）；`constraints.total_chars` 直接喂给 writer；`needs_history` 取代 _compose_run_task 的模式猜测——历史是否注入由任务卡显式声明。

## 2. Planner 执行位置

`session.chat()` 流程改为：

```
rewrite（如需）→ Planner.classify → TaskCard
  ├─ writer → LongWriter.write(goal, total_chars=constraints.get(...), plan=card.plan)
  ├─ agent  → AgentRunner.run(goal + constraints 摘要, ...)
  └─ qa     → 直接 generate
```

- Planner 失败（LLMFormatError）→ 回退 IntentRouter 规则路径 → 再失败默认 agent，任务卡用默认值填充
- 任务卡 emit `task.planned` 事件（含完整卡片）——**轨迹视图每轮首条渲染为任务卡记录**：目标、约束清单、计划步骤及逐步完成状态打勾——这就是 Plan 模式的雏形，也是"规划有了正式去处"的可视化证明

## 3. Verifier（验收关卡，纯代码）

`runner.run()` / `writer.write()` 的回答交付前过 `verify(answer, task_card) -> list[str]`（返回问题列表，空为通过）：

| 校验项 | 规则 |
|---|---|
| 思维链泄漏 | 含 `<think>` 残留或典型思考开头（"嗯，"/"我现在需要"/"首先，我得"）→ 不通过 |
| prompt 泄漏 | 含内部模板词（"可用工具"/"当前进度"/"只输出"等，从 prompts.py 自动生成词表）→ 不通过 |
| 字数约束 | task_card.constraints.total_chars 存在时，回答字数 < 目标 60% → 不通过 |
| 空/过短 | 回答 < 20 字且任务非简单问答 → 不通过 |
| 复读机 | 回答与任务卡 plan 文本重合度 > 80%（把计划当正文）→ 不通过 |

不通过的处理：emit `answer.rejected {reasons}`，**重试一次**（把问题列表注入 final_answer 提示词重新生成）；仍不通过则如实交付并附降级说明"该回答未通过验收：<原因>"——诚实优先，禁止假装成功。

## 4. 配套调整

- `config_schema` 新增：`planner_enabled: bool = True`（可关，退回旧三分类）、`verifier_enabled: bool = True`、`answer_max_retries: int = 1`
- 会话历史注入逻辑收敛：`needs_history=true` 才注入（qa 注入摘要、writer 注入相关素材轮、agent 注入压缩轮次摘要），替代 Phase 26-③ 的模式硬编码——两处逻辑合并，以任务卡为准
- Phase 13 的四个修复（思维链剥离、字数解析等）中，字数解析逻辑上移到 Planner（constraints 提取），writer 直接消费任务卡

## 注意事项

1. 本 Phase 与 Phase 26 有依赖：26 的思维链剥离先做（否则 verifier 的思维链校验会大量误伤），历史注入两处合并时以任务卡为准
2. Planner 会增加每次对话一次 LLM 调用（约 100ms~1s 延迟）——这是值得的：一次结构化理解换掉整轮跑偏
3. 任务卡是后续 Plan 模式、Goal 目标、子代理委派的共同地基：plan 字段天然是子任务清单，本期先把数据结构和轨迹可视化立住
4. 诚实预期：任务卡能让 4B 模型"流程正确地"写小说（类型对、字数够、结构完整），但文笔质量是模型能力上限——验收关卡保证的是"不交垃圾"，不是"交出杰作"。若创作质量不达标，把 writer 的段落生成路由到云端模型（Phase 14 的 llm-deepseek 已有路由能力）
