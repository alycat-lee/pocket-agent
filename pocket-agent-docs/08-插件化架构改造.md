# 08 · 插件化架构改造（Phase 13~16）

> 前置条件：Phase 0~12 完成。本阶段把 pocket-agent 从"内核 + 模块"重构为"插件运行时 + 一切皆插件"，架构理念对齐 DeepSeek Harness（DSH）的 Cordis 模型，Web 界面降级为可卸载插件。

## 1. DSH 概念到 pocket-agent 的映射

| DSH / Cordis 概念 | pocket-agent 对应实现 |
|---|---|
| 一切皆插件，无特权内核 | 内核只留插件运行时（加载、依赖、事件、回收），runner/session/writer/工具/UI 全部插件化 |
| Service Definition / Provider / Consumer 三角色 | 能力缝（seam）：每个可替换能力定义协议接口，插件提供实现，消费方只依赖接口 |
| 可逆效果（revertible effect） | 每次注册返回 disposer，插件卸载时逆序回收全部注册项 |
| 响应式依赖激活（spatial composability） | 插件声明 requires，依赖服务就绪才激活，消失则停用 |
| profile（web / headless 装配） | pocket.yml 声明启动哪些插件；web profile 挂 UI 插件，headless 不挂 |
| session log 投影 | 复用 Phase 11 的 checkpoint 事件流，后续演进为 append-only log |

**从 DSH 工程教训里抄来的三条纪律**（写进全局规则）：
1. 先问如何撤销，再问如何注册——每个注册必须返回 disposer，卸载测试必须验证注册项确实消失
2. 能力切分从消费方开始——先列"谁调用、需要什么稳定语义"，再定义接口；只有一个内部调用者的能力不升格为插件
3. 拒绝过度拆分——不为了"一切皆插件"把十几行逻辑也拆成插件

## 2. 插件运行时规格（runtime.py）

```python
from typing import Protocol, Callable, Any

Disposer = Callable[[], None]

class Context:
    """插件共享上下文。服务注册表 + 类型化事件总线 + 插件树管理。"""

    def provide(self, key: str, service: Any) -> Disposer:
        """注册服务，返回撤销函数。同 key 重复注册抛 PluginError。"""
    def require(self, key: str) -> Any:
        """获取依赖服务，未就绪抛 ServiceNotReady。"""
    def on(self, event: str, handler: Callable) -> Disposer:
        """订阅事件，返回退订函数。"""
    def emit(self, event: str, payload: dict) -> None: ...
    def mount(self, plugin: "Plugin", config: dict | None = None) -> None:
        """挂载插件：检查 requires 全部就绪 → 调 apply() →
        记录该插件产生的全部 disposer 到插件栈。"""
    def unmount(self, name: str) -> None:
        """逆序执行该插件的全部 disposer；若其他活跃插件
        require 了它提供的服务，拒绝卸载并抛 PluginInUse。"""

class Plugin(Protocol):
    name: str
    requires: list[str]          # 依赖的服务 key，如 ["llm", "tools"]
    provides: list[str]          # 本插件提供的服务 key
    def apply(self, ctx: Context, config: dict) -> None: ...

class PluginError(Exception): ...
class ServiceNotReady(PluginError): ...
class PluginInUse(PluginError): ...
```

装配配置 `pocket.yml`：

```yaml
profile: web            # web | headless
plugins:
  - name: llm-llamacpp
    config: { base_url: "http://localhost:8080/v1" }
  - name: llm-deepseek           # 可选：云端混合路由
    disabled: true
    config: { api_key_env: "DEEPSEEK_API_KEY" }
  - name: tools-core             # 内置演示工具
  - name: session
  - name: checkpoint
  - name: writer
  - name: ui-web                 # headless profile 下不加载
    config: { port: 3000 }
```

加载语义：按序挂载，某插件依赖未就绪时延迟到依赖出现后激活；任一插件 apply 抛错，已挂载部分全部逆序回收后退出（禁止半启动状态）。

第三方工具插件的标准形态——向 `tools` 服务注册并返回 disposer：

```python
class MyToolPlugin:
    name = "tools-weather"
    requires = ["tools"]
    provides = []

    def apply(self, ctx: Context, config: dict) -> None:
        registry: ToolRegistry = ctx.require("tools")
        disposer = registry.register_with_disposer(weather_tool)
        ctx.on_dispose(disposer)     # 注册进当前插件的回收栈
```

> ToolRegistry 需新增 `register_with_disposer()`：注册并返回注销函数。这是对 03 规格的一处小扩展。

## 4. Web UI 插件规格（ui-web）

- FastAPI + SSE：`POST /chat`（流式推送步骤事件与回答）、`GET /sessions`、`POST /resume/{run_id}`
- 事件来源：订阅 Context 事件总线（`step.start` / `step.tool_call` / `step.cache_hit` / `step.intercepted` / `answer.done`），AgentRunner 在各节点 emit——**把拦截和缓存命中可视化成界面标记，这是差异化亮点**
- 前端：单页静态文件（原生 HTML + EventSource），内嵌在插件包内，不做复杂构建
- headless profile 不加载本插件，其余功能完整可用——这是"UI 即插件"的验收标准
- 安全：写类工具（cacheable=False）执行前 emit `approval.required`，Web 层弹确认，超时默认拒绝

## 5. DSH / MCP 生态桥接（bridge-mcp 插件）

DSH 本体是 Node/TypeScript 生态（Cordis 为 TS 框架），直接二进制级复用其插件不现实；官方也是通过 MCP 与外部工具生态互通。因此桥接策略为 MCP 协议层对接：

```python
class McpBridgePlugin:
    """requires = ["tools"]
    apply()：
    1. 读取 config.mcp_servers（stdio/sse 两种 transport）
    2. 连接每个 MCP server，列出其 tools
    3. 每个 MCP tool 适配为 pocket_agent Tool：
       - schema 直接取 MCP inputSchema
       - fn 体内调用 MCP client，结果序列化为 str（源头压缩）
       - 写类工具标记 cacheable=False
    4. 返回批量 disposer，卸载时断开全部连接"""
```

反向能力（可选，后续）：把 pocket-agent 的工具通过 MCP server 暴露给 DSH 本体调用，实现双向互通。

## 执行顺序与注意事项

1. 严格串行：13 → 14 → 15 → 16。14 是大重构，动手前先 git commit 留退路
2. DSH 本体处于 developer preview，官方明示会有破坏性变更——桥接走 MCP 协议而不是绑定 DSH 内部 API，就是为了隔离这个风险
3. Phase 14 完成后，pocket-agent 的差异化定位：DSH 证明"一切皆插件"的架构上限，pocket-agent 在此之上叠加小模型专用机制（账本去重、压缩、护栏、约束解码）——这是 DSH 默认循环里没有的
4. 别拆过头：只有"确实有两个以上提供方"或"明确外部扩展需求"的能力才升格为插件，否则留在模块内
