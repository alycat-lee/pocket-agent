# 17 · 界面细节与停止响应（Phase 30）

> 四个小改动的诊断与修复规格。其中"停止无响应"是真 bug，根因不止一处。

## 诊断

| # | 需求 | 现状诊断 |
|---|---|---|
| 1 | 对话界面显示使用的模型 | 后端路由已有 provider 概念，但运行事件里没有携带"本次用的哪个模型"，前端无从显示 |
| 2 | 测试成功后回填模型 | `POST /api/providers/test` 已返回 `model_list`，前端 ProvidersCard 没有消费它 |
| 3 | 用户消息短文本右对齐、气泡随文字收缩 | 纯 CSS：`.msg-user` 缺 `width: fit-content; margin-left: auto; max-width` 约束 |
| 4 | 点击停止无响应 | **三处叠加**：① runner 只在步骤边界检查 `_stop` 标志，单次 LLM 调用（本地模型动辄 30s+）期间停止完全无效；② **writer 循环没有任何停止检查**——长文写作几十段根本停不下来；③ 前端点击后无即时反馈，用户无法判断点没点上 |

## 修复规格

### ① 模型显示

- 后端：`_sse_stream` 里路由完成后 emit `run.start {run_id, provider_name, provider_type, model}`；`answer.done` 的结算 payload 同样带上 provider/model
- 前端：会话页头（视图标签旁）显示当前生效模型徽章（默认 provider 的 model 名，hover 显示 provider 名称与类型 local/cloud）；轨迹视图的任务卡记录里显示本轮实际使用的模型
- 原则：显示的是**实际生效**的模型（路由后的结果），不是设置里的默认值——路由分流时 choose/fill 走本地、final 走云端，轨迹里每步的模型都应该真实可见

### ② 测试回填

- ProvidersCard：测试成功后——`model` 字段为空则自动回填 `model_list[0]`；`model_list` 多于 1 个时把输入框变为下拉选择（datalist 即可），全部可选
- 回填后提示"已自动选择模型 X，可修改"

### ③ 消息气泡

```css
.msg-user {
  margin-left: auto;        /* 右对齐 */
  width: fit-content;       /* 宽度随内容收缩 */
  max-width: 72%;           /* 长文本不超过 72% */
}
```

### ④ 停止响应（核心修复）

分三层：

1. **中断在途请求**：`OpenAICompatibleClient` 改用 `client.stream()` 发请求并持有当前 response 引用；新增 `abort_current()` 方法关闭在途连接（httpx response.close() 会让流式读取立即抛异常）。runner 的 `request_stop()` 联动调用当前 client 的 `abort_current()`——**停止从"步骤边界生效"变为"立即生效"**
2. **writer 循环接入停止**：每段开头检查 stop 标志；planner/qa 的单次调用经由同一 client 的 abort 机制覆盖
3. **前端反馈**：点击停止立即置按钮为"正在停止…"禁用态；收到 `stop_reason=stopped` 的结束事件后显示"已停止"并把已生成内容保留展示（部分内容不丢弃）；`run not found`（run 已结束）时静默恢复按钮态，不报错

兼容性注意：中断在途请求产生的异常要归类为 `LLMAbortedError`（新异常），runner/writer 捕获后走"优雅收尾"路径——已收集的信息保留，stop_reason=STOPPED，不当作失败重试。

````

1~2 秒内停下且已生成段落保留；页头显示当前模型；
````

## 注意事项

1. ④ 是本轮唯一动后端的改动，核心是"停止从协作式（步骤边界）升级为抢占式（中断在途请求）"——本地模型单次调用几十秒是常态，协作式停止在体感上等于没有
2. run.start 事件里的模型信息同时是轨迹视图的数据源：将来排查"为什么这次回答质量差"时，第一眼就能看到这次跑的是哪个模型
3. 气泡改动只有 CSS 三行，但验收时宽窄两种文本都要看一眼
