# 02 · 技术架构设计

## 1. 总体架构

```
┌─────────────────────────────────────────────────────────┐
│                      CLI / 调用方                         │
└──────────────────────────┬──────────────────────────────┘
                           │ run(task: str)
┌──────────────────────────▼──────────────────────────────┐
│              AgentRunner（状态机执行器）                   │
│   持有：执行循环、终止判断、护栏触发、步骤日志              │
└───┬──────────┬──────────┬──────────┬──────────┬─────────┘
    │          │          │          │          │
    ▼          ▼          ▼          ▼          ▼
┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐ ┌────────────┐
│ToolReg-│ │CallLed-│ │Context │ │LoopGu- │ │LLMClient   │
│istry   │ │ger     │ │Manager │ │ard     │ │(llama.cpp  │
│工具注册 │ │调用账本 │ │压缩拼装 │ │循环护栏 │ │ server 封装)│
└────────┘ └────────┘ └────────┘ └────────┘ └─────┬──────┘
                                                  │ HTTP
                                          ┌───────▼───────┐
                                          │ llama-server  │
                                          │ (Qwen3-4B Q4) │
                                          └───────────────┘
```

**核心原则：箭头方向即依赖方向，所有智能决策的原子化都收敛在 AgentRunner，LLMClient 是唯一接触模型的出口。**

## 2. 一次任务的执行时序

```
用户任务 "查北京和上海天气并比较温差"
  │
  ▼
AgentRunner.run(task)
  │  state = "尚无进展"; history = []
  │
  ├─► Step 1 ─────────────────────────────────────────
  │     ContextManager.build_choose_prompt(task, state, tools_topN)
  │     LLMClient.choose(prompt) ──约束解码整数──► 0 (get_weather)
  │     ContextManager.build_fill_prompt(task, state, schema)
  │     LLMClient.fill(prompt, schema) ──约束解码──► {"city": "北京"}
  │     CallLedger.check → 未命中
  │     执行 get_weather("北京") → 结果(1200字)
  │     ContextCompressor.compress → "北京：晴，25℃..."(≤300字)
  │     CallLedger.save; history.append
  │
  ├─► Step 2 ── 同上，选择 get_weather，参数 {"city": "上海"}
  │
  ├─► Step 3 ── 模型又选 get_weather {"city": "北京"}
  │     CallLedger.check → 命中！拦截，直接返回缓存
  │     history 记录 "[拦截重复]" 事件；LoopGuard.intercept_count = 1
  │
  ├─► Step 4 ── 选择 calculator {"expression": "25 - 18"}
  │
  ├─► Step 5 ── choose 返回 -1（信息足够）
  │
  ▼
ContextManager.build_final_prompt(task, history)
LLMClient.generate(final_prompt) ──► 最终回答
输出汇总日志（步数、缓存命中、拦截次数、终止原因）
```

## 3. 关键设计决策

### 3.1 为什么用"编号选择题"而不是让模型输出工具名

小模型生成精确字符串（工具名）容易拼错或幻觉出不存在的工具。输出整数编号：

- 输出空间从"任意字符串"压缩到 `{-1, 0..N-1}`，约束解码可 100% 保证合法
- 生成只需 1~2 个 token，快且稳定
- 幻觉在数学上不可能发生

### 3.2 为什么每次 LLM 调用都是无状态单轮

传统 Agent 把全部历史塞进一个持续增长的对话里，这正是小模型遗忘和重复的根源。本方案中：

- 记忆由框架的数据结构（`history: list[StepRecord]`）持有，不依赖模型"记住"
- 每次调用的 Prompt 由 ContextManager 当次按需拼装，只含本步必需信息
- 模型视角里永远是一个全新的、简短的、目标明确的单轮任务——这是小模型表现最好的形态

### 3.3 上下文预算分配（默认 3500 token 预算 / 8192 服务端窗口）

| 区段 | 预算（字符） | 内容 |
|---|---|---|
| system | ≤ 300 | 角色设定 + 硬规则（禁重复调用声明等） |
| 任务描述 | ≤ 200 | 用户原始任务 |
| 状态摘要 | ≤ 500 | "已完成 N 步：最近 3 步摘要" |
| 本步信息 | ≤ 400 | 候选工具列表 / 目标工具 schema |
| 历史记录 | 剩余额度 | 从最新往回塞，塞满即停 |

> 预算用字符数管理（中英混合按 1 token ≈ 1.5 字符粗估），不引入 tokenizer 依赖。

### 3.4 压缩策略：规则优先，模型兜底

- **规则截断**（默认）：超长结果保留头部 70% + 尾部 20%，中间标注 `[...截断 N 字...]`。确定性、零成本
- **LLM 摘要**（可选开启）：对搜索结果类文本调用 `summarize` 原子任务。注意摘要本身也是一次短上下文原子调用，输入同样先规则截断到 2000 字以内，防止压缩器自己超预算

### 3.5 护栏优先级

```
命中缓存拦截 → 记录 intercept_count
连续拦截 ≥ 2 → 终止（模型陷入重复意图，再循环无意义）
相邻两步原始输出完全相同 → 立即终止
步数 ≥ max_steps(10) → 终止
所有终止 → final_answer（基于已有信息作答，绝不裸异常）
```

## 4. llama.cpp server 配置要求

| 参数 | 值 | 理由 |
|---|---|---|
| `-c` | 8192 | 上下文窗口，低于此值压缩机制失去意义 |
| `--flash-attn` | 开启 | 降低 KV cache 显存占用，8G 显存必需 |
| `--cache-reuse` | 256 | Prompt 前缀复用，状态机每步 system 相同可提速 |
| 端口 | 8080 | 默认 |

框架请求参数（`LLMClient` 默认值）：

| 参数 | 值 | 理由 |
|---|---|---|
| temperature | 0.2 | 压低随机性，减少跑偏 |
| repeat_penalty | 1.1 | 抑制重复输出 |
| top_p | 0.9 | 常规配合 |
| response_format | json_schema | fill_args 步骤强制合法 JSON |

├── pyproject.toml
├── README.md
