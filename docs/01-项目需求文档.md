# 01 · 项目需求文档（PRD）

## 1. 背景与问题

在 8G 显存上运行的本地小模型（4B~9B 量化版）做工具调用 Agent 时，存在系统性短板：

| 现象 | 根因 |
|---|---|
| 同一工具被相同参数反复调用 | 上下文被截断/挤出，模型"忘记"已调用过；无框架层去重 |
| 输出内容重复、陷入循环 | 采样参数不当；无循环检测护栏 |
| 工具调用 JSON 解析失败后不断重试 | 小模型格式遵循弱，无解码层约束 |
| 长工具结果回填后模型跑偏 | 上下文预算无管理，关键信息被稀释 |
| 多步任务中途丢失目标 | 自由 Agent Loop 依赖模型的长程规划能力，恰恰是小模型最弱的环节 |

## 2. 项目目标

构建一个 Python 库 `pocket_agent`，将 Agent 的"智能"从模型侧转移到框架侧：

> **模型只做两种原子任务：单步选择（选择题）与参数填充（填空题），且每次都在短小、干净、受预算控制的上下文中完成；其余一切（流程、记忆、去重、格式、护栏）由代码保证。**

量化目标：

- 在 Qwen3-4B-Instruct（Q4_K_M）+ llama.cpp server 环境下，3~6 步的多工具任务**全程零重复真实调用**
- 单次 LLM 调用 Prompt 长度 ≤ 配置预算（默认 3500 tokens）
- 工具参数 JSON 解析成功率 100%（约束解码保证）
- 任何异常路径（模型乱选、工具报错、达到步数上限）都有确定性行为，不死循环、不抛裸异常

## 3. 范围

**包含**：核心框架库、内置演示工具、CLI 演示程序、单元测试与集成测试。

**不包含**：Web 服务封装、模型微调、向量数据库、多模型混合调度（作为后续扩展方向，架构上预留接口）。

## 4. 功能需求

### FR-1 工具注册机制

- 提供 `@tool` 装饰器，从函数签名 + docstring 自动生成 JSON Schema
- 每个工具需登记：名称、20 字以内短描述（供选择步骤使用）、JSON Schema（供约束解码使用）、执行函数
- 支持工具检索：当注册工具数超过阈值（默认 8 个）时，先用关键词匹配召回 top-N 候选再让模型选，避免全量 schema 挤占上下文

### FR-2 状态机执行器（AgentRunner）

- 框架持有执行循环，每轮依次执行两个原子 LLM 调用：
  1. `choose_tool`：输入任务、当前进度摘要、候选工具编号列表，输出一个整数编号（-1 表示"信息已足够，可以给出最终回答"）
  2. `fill_args`：输入任务、已知信息、目标工具的 JSON Schema，输出合法参数 JSON
- 每次 LLM 调用都是**无状态单轮请求**，上下文由 ContextManager 当次拼装
- 循环终止条件：模型返回 -1 / 达到 max_steps / 触发循环护栏

### FR-3 调用账本（CallLedger）

- 对每次工具调用计算指纹：`md5(tool_name + canonical_json(args))`
- 执行前先查账本：命中则**不执行真实调用**，直接返回缓存结果，并在历史中记录"拦截事件"
- canonical_json：键排序、去除空白，保证语义相同的参数生成相同指纹

### FR-4 语义级去重（可选模块）

- 对参数文本计算 embedding，与历史调用做余弦相似度比较，≥ 阈值（默认 0.95）视为重复
- 用于拦截"北京天气"与"北京市天气"这类表述差异
- embedding 模型可插拔，默认提供一个基于哈希的轻量级实现占位；不引入重型依赖

### FR-5 上下文压缩（ContextCompressor）

- **结果压缩**：单条工具结果超过 `per_result_limit`（默认 300 字符）时压缩——优先规则截断（保留头尾），需要语义摘要时调用 LLM 的 `summarize` 原子任务
- **预算拼装**：每次构建 Prompt 时按预算分配：system（≤300 字符）+ 状态摘要（≤500 字符）+ 本步信息（≤400 字符）+ 历史记录（从最新往回塞，塞满为止）
- 提供 token 估算工具（按字符数 ÷ 系数粗估，中英混合默认 1 token ≈ 1.5 字符）

### FR-6 约束解码（LLMClient）

- 封装 llama.cpp server 的 OpenAI 兼容接口（`/v1/chat/completions`）
- `fill_args` 步骤使用 `response_format: {type: "json_schema", ...}` 强制输出符合工具 schema 的 JSON
- `choose_tool` 步骤使用 schema 约束输出整数（`{"type": "integer"}`），或退化为正则提取兜底
- 统一采样参数：temperature 0.2、repeat_penalty 1.1、top_p 0.9（可通过配置覆盖）

### FR-7 循环护栏

- `max_steps`：硬性步数上限，默认 10
- 重复拦截计数：连续被账本拦截 ≥ 2 次，强制终止循环并基于已有信息生成回答
- 输出重复检测：相邻两步模型原始输出完全相同，触发终止
- 所有终止路径都必须走到 `final_answer` 步骤，给用户提供基于已有信息的回答，不裸奔异常

### FR-8 可观测性

- 每步输出结构化日志：步骤号、选择的工具、参数、是否命中缓存、Prompt 估算 token 数、耗时
- 运行结束输出汇总：总步数、真实调用次数、缓存命中次数、拦截次数、终止原因

### FR-9 CLI 演示

- 命令：`pocket-agent demo "查询北京和上海的天气并告诉我温差"`
- 内置演示工具（全部 mock，不依赖外部 API）：`get_weather`、`calculator`、`read_file`、`get_current_time`
- 打印每步决策过程与最终结果

## 5. 非功能需求

- Python ≥ 3.10；核心依赖仅 `httpx`、`pydantic`；embedding 等可选功能走 extras
- 核心模块单元测试覆盖率 ≥ 80%；账本、压缩、护栏逻辑必须有纯单元测试（不依赖真实 LLM，用 MockLLM）
- 所有 LLM 交互通过 `LLMClientProtocol` 抽象，测试时可注入假实现
- 代码风格：类型注解全覆盖，ruff 检查通过

## 6. 验收标准

| 编号 | 标准 | 验证方式 |
|---|---|---|
| AC-1 | 多工具任务零重复真实调用 | 集成测试 + demo 日志 |
| AC-2 | 参数 JSON 解析成功率 100% | 约束解码集成测试 |
| AC-3 | 单次 Prompt ≤ 预算 | 日志断言 |
| AC-4 | 达到 max_steps 优雅退出并给出回答 | 单元测试（MockLLM 永远返回同一选择） |
| AC-5 | 工具抛异常时循环不崩溃，错误信息进入历史 | 单元测试 |
| AC-6 | 核心模块覆盖率 ≥ 80% | pytest-cov |
